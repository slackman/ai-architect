# ДЗ4. Выбор способа хостинга LLM

## Title

**ADR-004-HW: Использовать облачный API моделей для MVP, сохранив локальные эмбеддинги.**

## Status

**Принято для MVP.**

## Context

Система анализирует бухгалтерские документы: договоры, акты и платёжные поручения. Пользователь загружает PDF или сканы и задаёт вопросы. Система находит доступные источники, связывает документы по договору и возвращает ответ с цитатами. Суммы рассчитывает код через `Decimal`.

Модели нужны для трёх задач: OCR сканов, извлечения реквизитов и генерации ответов по найденным фрагментам. Эмбеддинги используются для векторного поиска в Qdrant. Поэтому альтернатива внешнему API должна покрывать не только текстовую генерацию, но и распознавание изображений.

### Условия принятия решения

- MVP на синтетических документах. Нужно проверить сквозной сценарий загрузки, поиска, расчётов и ответов с источниками.
- Приложение и хранилища развёртываются через Docker Compose. В текущем составе нет сервера LLM/VLM и выделенного GPU-контура.
- Пока нет подтверждённой серии измерений объёма модельных вызовов, токенов и итоговой стоимости API. Экономическое преимущество self-hosted при большой нагрузке пока не доказано.
- Права пользователей проверяются до отправки контекста и перед выдачей ответа. Однако разрешённые фрагменты, тексты для извлечения реквизитов и изображения для OCR покидают контур приложения.
- Сравнение качества облачной и локальной моделей на одном размеченном корпусе не проводилось.

### Рассматриваемые варианты

**A. Облачный сервис моделей:** приложение вызывает внешний API через OpenRouter. В профиле MVP для текста и изображений указана `qwen/qwen3.7-flash`.

**B. Self-hosted:** развернуть модель с открытыми весами в собственном контуре и обслуживать её самостоятельно. В целевой архитектуре предусмотрены LiteLLM и vLLM с Qwen3.6-35B-A3B. Для полного замещения внешнего API необходимо также обеспечить OCR/VLM.

### Сравнение вариантов

| Критерий | Облачный API – текущий MVP | Self-hosted – альтернатива |
|---|---|---|
| **Стоимость** | Не нужно выделять GPU для LLM/VLM и разворачивать сервер моделей. Возникают расходы на вызовы OCR, извлечения и генерации. Фактическая сумма за месяц не измерена. | Нужно учитывать GPU/сервер или аренду, хранение весов, эксплуатацию, обновления и резервирование. Окупится ли такой контур относительно API, зависит от нагрузки и производительности выбранной модели. |
| **Безопасность данных (Privacy)** | Сканы и тексты документов передаются внешнему провайдеру для распознавания и генерации ответов. | При полностью локальной обработке OCR и LLM содержимое документов можно хранить внутри своего контура. Защита сервера, сетевого доступа, журналов и секретов остаётся ответственностью команды. |
| **Качество ответов** | Есть зафиксированные сквозные проверки с внешней моделью: обработка документов и ответы с источниками. Это подтверждает работоспособность сценария, но не превосходство над локальной моделью. | Эквивалентность качества не проверена. Нужно отдельно оценить русскоязычный OCR, реквизиты, JSON-ответы и точность цитат на том же корпусе. |

Это единичный замер, не p95 и не SLA. | Устраняется внешний сетевой переход, но время зависит от модели, оборудования, длины контекста и очереди. Для локальной модели измерений нет. Меньшая задержка не гарантирована. |
| **Сложность поддержки** | `ModelGateway` и настройки уже реализованы. Команда поддерживает интеграцию, ключи и обработку ошибок, а не сервер инференса. Остаётся зависимость от доступности API. | Нужно развернуть и сопровождать сервер, GPU-драйверы, веса, совместимость API, очередь и мониторинг. Это расширяет текущий контур. |

Источник результатов и границ измерений: [отчёт проверок](../docs/testing-report.md) и [результат сквозного запроса с обращением к LLM](../docs/benchmarks/ai-query-current-e2e.json). Нагрузочный тест списков документов из отчёта не включает LLM/OCR и не используется для оценки задержки моделей.

### Обоснование стоимости

Облачный API оплачивается по фактическому использованию. Self-hosted требует затрат на оборудование или аренду и сопровождение моделей. Нагрузка и расходы MVP пока не измерены, поэтому экономическое преимущество одного варианта не доказано. На текущем этапе облачный API выбран, поскольку интеграция уже работает и не требует развёртывания отдельного сервера.

## Decision

**Для демонстрационного MVP использовать облачный API через OpenRouter для OCR, извлечения реквизитов и генерации ответов. Эмбеддинги оставить локальными.**

1. Использовать существующий `ModelGateway` и профиль `qwen/qwen3.7-flash` для `TEXT_MODEL` и `VISION_MODEL`. Адрес API и модели задаются настройками.
2. Сохранить локальный FastEmbed с `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, размерность 384. В выбранном профиле векторизация документов и вопросов не требует внешнего API эмбеддингов.
3. Оставить оригиналы и прикладные хранилища в собственном контуре. Во внешний API передаются изображения страниц для OCR, тексты страниц для извлечения реквизитов, а при генерации – вопрос, доступные фрагменты и расчёты. Локальное хранение оригиналов не означает, что их содержимое не передаётся наружу.
4. Применять существующие проверки tenant/ACL, валидацию реквизитов и цитат, расчёты в коде и файловые секреты. Эти меры ограничивают доступ пользователей и проверяют результат, но не заменяют контроль обработки данных у провайдера.
5. Не разворачивать self-hosted LLM/VLM в рамках текущего MVP. Рассматривать развёртывание локального контура как отдельный следующий этап.

## Consequences (Pros/Cons)

### Плюсы

- Можно демонстрировать полный сценарий на существующей интеграции без отдельного развёртывания LLM/VLM и выделения GPU.
- Усилия направлены на проверку ценности системы: связи документов, точные суммы, права и ответы с источниками.
- Локальные эмбеддинги исключают отдельные внешние вызовы для векторизации и сохраняют текущую схему поиска.
- Шлюз и конфигурируемый адрес API дают основу для смены поставщика или перехода к локальному совместимому серверу.

### Минусы и принятые компромиссы

- **Данные покидают контур.** Модель получает контекст до маскирования персональных данных в ответе. Отзыв прав во время генерации может заблокировать выдачу ответа, но уже отправленный текст отозвать нельзя.
- **Внешний API – зависимость сквозного сценария.** Ошибки и ограничения сервиса могут сорвать обработку или ответ. Автоматического переключения на локальную модель в MVP нет.
- **Нет доказанной предсказуемости стоимости и задержек.** Лимиты размера файлов, контекста, частоты запросов и выхода ограничивают отдельные операции, но не являются месячным денежным бюджетом или гарантией p95.
- **Качество не подтверждено полноценным сравнением.** Работоспособность на небольшом синтетическом корпусе не доказывает точность на реальных сканах. Проверки цитат и схем не гарантируют истинность каждого утверждения.
- **Перенос потребует проверки совместимости.** Смена URL и имени модели не гарантирует поддержку изображений, параметров запроса и JSON-ответов. Локальный сервер нужно интегрировать и проверить на тех же сценариях.

### Когда пересмотреть решение

| Триггер | Что необходимо для нового решения |
|---|---|
| Переход к реальным документам с запретом внешней обработки | Пересмотреть ADR до передачи данных. Проверить полностью локальный OCR/LLM-контур и его защиту. |
| Подготовка пилота с реальными данными, если внешняя обработка допускается | Установить допустимые категории данных, условия хранения и обработки у посредника и конечного провайдера, необходимые ограничения передачи. Текущий ADR этого не подтверждает. |
| Устойчивая нагрузка и существенные расходы API | Собрать число вызовов, токены/изображения и счета. Сопоставить с полной стоимостью локального контура при сопоставимом качестве и пропускной способности. |
| Не выполняются требования по качеству, задержке или доступности | Зафиксировать требования, провести одинаковую серию проверок облачного и локального вариантов. Измерить OCR, извлечение реквизитов, обоснованность ответов, p50/p95 и ошибки. |

## Pitch для CTO

Для текущего MVP выбираем внешний API моделей через OpenRouter: у нас уже работает обработка синтетических бухгалтерских документов и ответы с источниками, а отдельный GPU-контур в MVP не развёрнут. Именно в этих условиях это обоснованный выбор: он позволяет проверить полезность продукта без добавления задачи эксплуатации LLM/VLM, при этом поиск и эмбеддинги остаются локальными. Мы принимаем зависимость от API, переменные расходы и передачу содержимого документов провайдеру. Единичный замер 2,48 секунды подтверждает только выполнение конкретного запроса, не SLA. До перехода к реальным конфиденциальным данным пересмотрим допустимость внешней обработки, а при устойчивой нагрузке сравним полную стоимость и качество с локальным контуром LiteLLM/vLLM.
