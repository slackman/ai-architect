# ADR-005: Серверный доступ и проверки ответа

## Контекст

Открытый договор может быть связан с актом, доступным только бухгалтеру.
Ограничения доступа должны учитываться при поиске и подготовке контекста модели.

## Решение

Персональный токен определяет пользователя и его группы на сервере.
Бухгалтер имеет доступ к `shared` и `finance`, читатель - к `shared`.
Токены, ключ модельного API и пароли хранилищ передаются через файлы
Compose secrets, исключённые из Git и образа. В PostgreSQL хранятся хэши
пользовательских токенов.
Qdrant и Neo4j фильтруют источники по tenant и группам. PostgreSQL повторно
проверяет права перед генерацией и выдачей ответа. Проверки применяются также
к оригиналам и истории. Код блокирует известные шаблоны подмены инструкций,
проверяет идентификаторы цитат и маскирует некоторые персональные данные в ответе.

## Альтернативы и причина выбора

Проверка только в интерфейсе оставила бы прямые запросы к API без контроля.
Фильтр только в индексе зависит от актуальности его копии прав.
Поэтому окончательная проверка выполняется по PostgreSQL.
Два заранее заданных токена позволяют проверить различия доступа без настройки
системы входа. В целевой архитектуре вход и управление учётными записями
обеспечивает Keycloak. Права на документы продолжает проверять приложение.
Файловые секреты выбраны для запуска на одном сервере без отдельного
хранилища секретов.

## Допущения и ограничения

Пользователи заданы заранее. Интерфейса управления правами нет.
Секреты на сервере меняются вручную. Автоматической ротации нет.
Отзыв прав во время генерации блокирует выдачу ответа, но уже отправленный
в OpenRouter текст отозвать нельзя. Проверки подмены инструкций охватывают известные
шаблоны. Персональные данные маскируются в ответе после генерации. Модель получает контекст документов до маскирования.
